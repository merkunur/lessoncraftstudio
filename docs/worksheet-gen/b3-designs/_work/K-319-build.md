## Deviations from the design file (each with the measurement)
1. **No design-named NEW component is consumed by the base.** §2 lists `faceTile / faceChoiceRow / sceneRow / sceneCard / sceneGrid / blankFace / checkInCard` — all face-only (F1/F2/F5) — and says the base reuses `.ws-match*` inline. The brief requires a components file, so the base's column pair is exported as type-scoped `feelingFaceTile / feelingWordTile / feelingMatch` (the lit-vocab-match idiom on the page.css chrome). The face components are NOT exported (nothing on the base consumes them — the K-317 convention). The design's `matchColumns` is "defined by G1-307 in a file that does not exist"; the `feeling…` names cannot collide with it when G1-307 lands.
2. **The body is not 722 px; the stack is shrinkable instead of re-budgeted to one number.** Measured in the real render (`render-instance.js`, file:// fonts): en chrome → body **778**; a 70-char de title (3 lines, head 112) + 150-char instruction (2 lines, 46) → **733**; a 70-char fi title with long words wraps to **4 lines** (head 145) → **700**, where the design's rigid 6 × 108 + 5 × 12 = 708 stack printed the last row 14 px into the attribution band (footer lint fired). A 150-char instruction never reaches 3 lines at 631 px (2 lines), so the README's "3-line title + 3-line instruction = 722" is not the worst legal case — the 4-line title is. Fix: every tile is `flex:0 1 auto; height:itemH; min-height:max(picPx+16, wordPx+24)` and `.ws-match` + both `.ws-match-col` carry `min-height:0`, so the rows squeeze evenly (108 → 104.7 at 700, face 80 still inside 104) and space-around still spreads them at 778. The design's numbers (108 / 168 rows, 80 / 100 / 72 faces, 160 / 180 / 260 tiles) are unchanged at every body ≥ 720. The gate fixes both chrome fixtures and the P15 poison is the rigid stack under the fi chrome.
3. **Root stamp for the faces:** the design stamps `data-lcs-face="base|scene|…"` on the ROOT and `data-lcs-face="<id>"` on the LEFT TILES — one attribute name, two meanings; `querySelectorAll('[data-lcs-face]')` would return both. The base stamps the root `data-ws-content data-lcs-feelings data-lcs-pairs="N"` and nothing else (byte-identical when a face lands); Phase 2 should stamp the face's layout as **`data-lcs-layout`**, not `data-lcs-face`.
4. **The EN bank holds 11 faces, not 6.** §5's shape carries `valence` for the F3 sort, so the five valence-only faces (merry content excited / capricious disgusted) are in the bank with `matchable:false`; the validator's rule 1 makes `matchable:true` ≡ the six accepted ids (poison P1), and rule 4 counts ≥ 3 per bin (good 4 / bad 5). The base never prints them.
5. **`OPENED_CUES` lives in the gate** (design: "the human open IS the gate" for P2). The list is the 12 pictures opened above with the feeling each honestly cues; a scene object outside it FAILS, so a merely-resolving cue (the smiling ghost) cannot enter the bank. A panel that adds a scene must open it AND the builder extends the list — a deliberate two-key lock.
6. **`gate-emotions-data.js` is not a separate tool**: the design's node cross-check (every `[data-lcs-word]` text === bank word) runs inside `verify-b3-feelings.js` `assertRender` (poison PW). The batch's `tools/validate-b3-draft.js` (absent) should import `validateBank` from the gate rather than re-author the rules.
7. **Word tile text colour** is `T.ink` (design palette lists ink); lit-vocab-match prints teal. Ink on cream at 28 px is the higher-contrast read for a K decoder; a one-token swap if the panels prefer teal.
