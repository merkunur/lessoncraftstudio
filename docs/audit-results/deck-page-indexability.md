### ⚠️ M3 (MEDIUM) — Cloudflare-managed AI-bot Disallow contradicts operator-intended posture

The robots.txt has TWO `User-agent: *` blocks (Cloudflare-managed + LessonCraftStudio):

```
# Cloudflare-managed (generated by Cloudflare proxy)
User-agent: *
Content-Signal: search=yes,ai-train=no
Allow: /

User-agent: Amazonbot
Disallow: /

User-agent: ClaudeBot

```

**Issue:** GPTBot, CCBot, Google-Extended, ClaudeBot, etc. have CONFLICTING directives between the two blocks. Most crawlers respect FIRST-match for User-agent rules; some merge; behavior varies. The Cloudflare-managed block effectively blocks them.

**Per CLAUDE.md §3.5:** "AI crawler bot policy set to 'Do not block (allow crawlers)' preserving §17.4 acquisition-strategy alignment." Operator's intent is to ALLOW AI crawlers. The Cloudflare-managed block contradicts this for: Amazonbot, Applebot-Extended, Bytespider, CCBot, ClaudeBot, CloudflareBrowserRenderingCrawler, Google-Extended, GPTBot, meta-externalagent.

**SEO impact:** AI-crawler blocking weakens the §1 SEO+embed-virality acquisition flywheel insofar as AI search surfaces (ChatGPT browse, Perplexity, etc.) reference the platform. Major search-engine indexability (Googlebot, Bingbot) is unaffected — those bots are NOT in the Cloudflare Disallow list.

**Remediation:** Cloudflare dashboard → AI crawler bot policy → confirm "Do not block (allow crawlers)" is set; the per-bot Disallow block is auto-generated by Cloudflare from this setting. Operator-side verification needed.

### 🔴 H1 (HIGH) — English-text intermixing in es deck title + meta description

**9 of 11 es decks (82%)** have English app-name/worksheet-name text in their title + description. Only 2 of 11 are fully Spanish:

✓ **Fully Spanish:**
- es addition-image-image: "Suma Divertida Ficha"
- es wordsearch: "Sopa de Letras Hoja de ejercicios"

❌ **English-intermixed:**
- es matching-letter, chart-count, odd-one-out, math-worksheet, bingo, pattern-train, sudoku, word-guess, word-scramble — all carry English app-name (Picture Bingo / Sudoku / Match Up / Picture Graph / etc.) + English description text ("Free interactive [English worksheet name] for [Spanish level]. Print or play online.")

**SEO impact:**
- Title + meta description are LOAD-BEARING signals for locale-relevance ranking in Google's per-locale search.
- Mixed-locale text confuses Google's per-locale ranking algorithm. Spanish-search users see English app-names in SERP snippets; reduces click-through.
- Per CLAUDE.md §17.4: native-language slugs principle applies to title + description content too — Spanish deck pages should have Spanish titles + descriptions to rank in Spanish search.

**Remediation path (recommended `[FIX][SEO]` follow-on commission):**
- Source of mismatch: deck.html `<title>` + `<meta description>` substitution at publish-cli upload time per CLAUDE.md §15.2 step 4 + §17.8.5 substitutes `__EDUCATIONAL_LEVEL_LOCALIZED__`. The localized-level substitution works (Spanish levels render correctly: "Jardín de infancia," "1.º de primaria"). The app-name + description-template substitution does NOT have a locale-aware variant.
- Per §17.8.1: title pattern is `<Exercise type, capitalized> Worksheet — <Theme, capitalized> — __EDUCATIONAL_LEVEL_LOCALIZED__ | LessonCraftStudio`. The "Worksheet" + theme-localization happens to use English app-name + theme strings even on es pages.
- Fix scope: extend per-locale title/description-template lookup in publish-cli OR catalog-export.js's `buildSeoHead` helper. Touches `REFERENCE TRANSLATIONS/catalog-export.js` (per-locale title-template + description-template strings) + 11-locale string population.

**Estimated effort:** small `[FIX][SEO]` commission. Per-locale string authoring × 11 locales × ~3 string templates each = ~33 strings + helper extension. Affects ALL future deck-page authoring across all locales.

### ⚠️ M1 (MEDIUM) — Hreflang absent on all 18 sampled deck pages

All 18 sampled pages have **0 `<link rel="alternate" hreflang="...">` tags.**

**Per CLAUDE.md §17.8.7:** v1 vs v2 split — "v1 decks (`content_family_id = null`): the marker is replaced with an empty string. No hreflang block is emitted." This is **expected v1 state**; not a regression.

**However**, the 7 en+es paired slugs (sudoku, bingo, chart-count, matching-letter, math-worksheet, odd-one-out, pattern-train) ARE pedagogically equivalent content — they should be hreflang-paired even if not v2-translation-tracked. The current state means Google sees them as separate documents without explicit alternation signal.

**Doctrine gap:** the v2 translate-this-deck workflow per §17.8.7 is the canonical hreflang activation mechanism. Until v2 ships, no hreflang. But for the 7 currently-paired slugs (en+es at the same canonical app-base slug), an inferred-hreflang opportunity exists at publish-cli — same `(app, mode)` combination across en+es could be hreflang-paired by inference even without `content_family_id`.

**Estimated effort:** medium `[FIX][SEO]` commission OR amendment to v2 spec. Touches publish-cli's hreflang substitution logic + `Deck` table query for cross-locale-same-slug-content matching.

**Not a blocker for Arc 7 Phase 3** — pt sparse-override authoring is at the lesson-plan layer, not the deck-page layer; doesn't compound this issue.

### ⚠️ M2 (MEDIUM) — Open Graph metadata absent (deferred-queue per §15.7)

All 18 sampled pages have **0 `<meta property="og:...">` tags.**

Per CLAUDE.md §15.7 deferred-queue: "OG metadata on /[locale]/decks/[slug]" filed as deferred. **Known gap, not a regression.**

Per CLAUDE.md §15.14 + §17.8.15: OG image generation IS in publish-cli's pipeline (1200×630 derivation step at `/var/www/lcs-media/decks/<locale>/<slug>-v<N>/og-image.png`); the asset is generated but the deck.html doesn't reference it via `<meta property="og:image">`.

**SEO impact:** social-sharing previews (Pinterest, Facebook, Twitter) fall back to default text-only or wrong-source preview. Pinterest is identified as the strongest non-SEO acquisition channel for the multilingual K-3 audience per CLAUDE.md §9 launch goals — degraded Pinterest preview directly weakens that channel.

**Remediation:** small `[FIX][SEO]` commission extending publish-cli's `buildSeoHead` to emit `<meta property="og:title">`, `<meta property="og:description">`, `<meta property="og:image">` (referencing existing og-image.png), `<meta property="og:type" content="website">`, `<meta property="og:url">`, `<meta property="og:site_name">`, plus Twitter Card variants (`twitter:card`, `twitter:title`, etc.).

**Per CLAUDE.md §17.8.1:** the spec lists Schema.org JSON-LD + canonical + title + meta-description as the deck.html SEO surface MINIMUM. OG tags were not in the original §17.8.1 spec. Adding them is a forward-looking enhancement; not a regression-fix.
