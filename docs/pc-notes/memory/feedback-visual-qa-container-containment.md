   🆕 **TEXT-CLIP (added 2026-07-15, `a0537dc5`) — the class the harness was BLIND to.** `-webkit-line-clamp` + `overflow:hidden` silently deletes copy past its line budget, and **nothing else here can see it**: the clamp is BY DESIGN, so the node reports no overflow (OVERFLOW measures the *document*), its box is exactly the intended size (FITS/SPARSE are happy), and the sentence just vanishes. Only `scrollHeight > clientHeight` on the clamped node detects it — the **vertical twin of the existing HEADER-CLIP** (which is `scrollWidth > clientWidth`, and covers only the shell title). ⚠ **Scoped to real `line-clamp` nodes on purpose — do NOT widen to bare `overflow:hidden`**, which containers use for rounded corners/masks with children legitimately extending (false positives). **41 activity files use line-clamp** → the class is now caught per-activity when next touched (§A.13.60 "convert when next touched"); they were NOT swept retroactively (each clip needs a native copy decision).

An activity with **>8 rounds ships rounds 9+ NEVER MEASURED at any viewport.** Mending Basket (#6) had **15 rounds** → 7 unmeasured → match/sort/sequence cut off at desktop with the **Check button below the 900px fold**. I "verified" with `fullPage:true` probe screenshots, but the wrapper sets `html,body,#lcs-root{height:100%}` so the document height = the viewport (900) and everything below is **silently clipped** — the probe PNG looked complete but the cut-off was hidden. **Fixit (#5) had the SAME defect** on its round-9 balance render (only caught when I re-ran uncapped). **FIX (done):** cap raised to `Math.min(N, 40)`; the sweep now measures EVERY round. **RULES, permanent:** (a) the sweep is only trustworthy UNCAPPED — it MUST report `<actual round count> round(s)`, never "8 round(s)" for a longer activity; (b) NEVER trust a `fullPage` probe to prove FITS — the `height:100%` body clips below the fold; use the harness's MEASURED control-bottom (getBoundingClientRect sees beyond the viewport), not a screenshot's apparent completeness; (c) after ANY multi-round activity, confirm the sweep line says the full round count; (d) the long-prompt + tall-board combo (a 2-3 line shell prompt eats ~120px at the narrow desktop prompt column) is the usual cut-off cause — keep `strings.prompt` to ONE short line, and lay tall boards (stacked twin-scenes) side-by-side on desktop via `@media(min-width:600px)`.

The operator caught fruit **floating above** the Echo Grove baskets after I declared the activity "good" from my own screenshot glance. **Why:** HTTP-200 + functional gates + a casual screenshot look is NOT visual approval. **How to apply:** after building/changing ANY activity, run `scripts/visual-qa-activity.js` (above) THEN spawn a **visual-critic agent** (general-purpose — it Reads the rendered PNGs; agents see images) to inspect the FULL viewport sweep **at the densest round + the narrowest width (320px) + DESKTOP 768 AND 1024** against the 14-point rubric below. Fix every flagged defect → re-render → re-run until clean. ONLY THEN is it eyeball-ready for the operator. This is part of the per-activity definition-of-done, alongside the functional gates ([[project_activities_live_inventory]], §20.4/§A.13.55).

**STYLE-CLASH RULE (the big one — operator was furious, 2026-06-23): NEVER put real photographic/3D-rendered library images inside a HAND-DRAWN faux-3D container** (a drawn "basket"/"bowl"/"crate"). Flat 2-color line-art trying to be a 3D *object* next to realistic 3D props ALWAYS loses — it reads as "expensive stock art dumped on cheap clip-art," amateur. The more "basket-y" the drawing, the worse the clash. Echo Grove's drawn baskets read as crude striped boats with fruit floating on top; ~10 geometry iterations could not save the approach because the approach was wrong. **The fix: stop drawing a vessel; draw soft GROUND.** Present grouped real-image props as **fruit resting on a soft, flat, pale-teal PLATE (a soft `<ellipse>`, whisper rim) + soft contact shadows** under each item (blurred ellipse via one shared `<filter><feGaussianBlur>`), so the SVG RECEDES instead of competing. Plate must FRAME the cluster with margin (no item hanging off); keep clusters small + spread (≤4 in a single row; 5→3+2, 6→3+3) so contact shadows don't pool. Reference impl: `echo-grove-activity.js plate()`. This is now the standard for grouping library-image props — NOT a drawn container.

**The earlier "objects in a vessel" technique** (Mochi's bowl, where the vessel belongs to a CARTOON character's world so the clash is muted): draw container BACK → objects nestled DOWN → an **OPAQUE FRONT WALL drawn AFTER the objects**. A stroke/outline is NOT containment. Use this ONLY for a character's own cartoon vessel; for standalone grouped props use the soft-plate approach above.

**12-point visual-QA rubric:**
- Containment: (1) opaque FRONT WALL after the objects (not a stroke); (2) object centres at/below the rim, piles grow up from the floor; (3) nothing floats above the container (check densest/multi-row case).
- Baseline: (4) nothing hovers with a background gap beneath (check SVG-part seams: lid↔bowl, handle↔body).
- Proportion: (5) container outweighs contents (objects ≤~60-70% of a column; real depth below the rim); (6) believable relative sizes.
- Recognizability: (7) container reads as the NAMED thing (basket=weave/lip/taper; bowl=depth) — not a generic cup.
- Overlap/occlusion: (8) handles/rims occluded by the load where they should be (nothing laced through a pile); (9) no clip/overflow 280-768.
- Density: (10) at max count every object stays individually countable (≤~30% overlap, tops/sides clear of the front wall + each other).
- Alignment/warmth: (11) multi-card layouts share footprint (no unintended salience tell); (12) warm, intentional — no amateur gaps/crossed-lines/sitting-on-a-line artifacts.

- Layout/off-fold: (13) the activity must not be so TALL that answer options fall below the fold (operator caught Echo Grove TWICE: 3 cards stacked → 3rd option + Check cut off on a phone). **Fix: a responsive GRID that goes 2-up on phones** — `grid-template-columns:1fr` default, `@media(min-width:340px){…1fr 1fr}` (2-up at phone width), `@media(min-width:560px){…1fr 1fr 1fr}` (row of 3 on desktop); put `min-width:0` on the card. 2-up halves the card-block height vs a 3-tall stack AND keeps cards countable (a 3-across row at phone width makes fruit too small). **MEASURE the rendered `.lcs-app` height + cards-per-row at 280/360/412/600/768** — at 360px the height must fit a phone (~≤720px) so all options + Check are on-screen; auto-fit `minmax()` is unreliable (container-width-dependent) → use explicit `@media` viewport breakpoints. Verifying horizontal overflow alone is NOT enough; measure HEIGHT.

- Grouped-real-image layout (14): to show "g groups of s" with real images and NOT look cheap (tiny fruit / sparse cards / unbalanced option-count) — operator was furious through ~6 iterations — use **full-width "rail" cards that STACK**: each candidate card spans the width and is SHORT (a single horizontal row of plates); plates lay at their NATURAL width CLUSTERED + CENTERED (scale down only if too many to fit — NEVER spread `space-between`, which leaves a dead center gap); fruit sized from card HEIGHT to FILL the plate (big). Stacking short wide cards = big fruit AND fits a phone AND makes 2-option and 3-option rounds equally balanced (a stack of 2 or 3, no empty grid column). Cap card max-width (~400px) so full-width cards don't balloon tall on desktop. Do NOT use a side-by-side card grid (starves width → tiny fruit) and do NOT spread plates to card edges.

**Process:** inspect the rendered PNG at the DENSEST case + the NARROWEST width + a typical desktop width (≈600-768, for the off-fold/row check); MEASURE rendered height at phone width. Tests-pass / HTTP-200 is NOT visual approval. When a layout/visual keeps failing, get a senior-designer AGENT to diagnose the ROOT architecture (not tweak), and verify with my OWN eyes on the pixels before claiming done.
