## Deviations from §3 (each measured)

1. **F4's second attribute is a PICTURE theme, not `colors`** (the task's RULING: a non-colour attribute if the bank offers one). The six colour drops measure luma 88-182 with one silhouette (`_work/G2-319-build.md`): a hue-only difference prints as the same grey drop, and a colour WORD would print a noun (the family boundary forbids it and needs 11-locale agreement). Every theme allowlist was opened at 36 px grey, so a second theme is the honest apparatus: `attr2:['fruits','pets']` (fruits ∩ {pets, toys, vehicles, farm animals, zoo animals} = ∅, pets ∩ fruits = ∅; the build asserts the two allowlists share no picture and refuses otherwise). The `pc` row headers are attr-2 pictures (the design wanted colour drops there; pictures fit the same 56 px cells). **Title re-keyed** from "Which Pet, Which Colour" to **"Two-Attribute Logic Puzzles: Two Pictures per Child"** (49 chars) and the instruction to "Each child has one picture from each set. Use the linking clues to fill all three grids." — the old title named a set the child never sees (and "pet" was theme-specific on a six-theme fan anyway). Bank `strings.F4` updated in step (the gate asserts row = bank = emitted spec). `SETS.distinct.colors` stays in the bank (unused; `validateBank`'s ≥ 6 check still passes).
2. **F3 d2 is `clues:[2,3]` with `pageMin:{pos:1}`, not `clues:[3,3] maxPos:1`.** On a 3×3 a positive clue fixes a row and one negative settles the other two, so a unique set with a `pos` has EXACTLY two necessary clues (the base's 69 % note is 100 % here): `clues:[3,3]` + `pos` is unsatisfiable, and the first gate sweep produced neg-only pages on 6 seeds × 6 themes (0 ringed pictures). §3's own F3 d1 is "2 picture clues pos + neg"; d2 now spans 2-3 (2 clues 76 % of cases, as the base's d1) and `pageMin:{pos:1}` guarantees a teal "has" ring on every page so the two pictograms are both taught. The EN instruction now names both: "A crossed-out picture means the child does not have it, a ringed one means the child has it. Cross out on the grid, then circle each answer." (139 chars).
3. **F3 cells 56, not 60.** With the design's 60 the stack is 36 + 12 + 2 × (244 + 8 + 72) + 20 = 716, which fails the measured 710 (3-line title + 3-line instruction) and 700 (4-line fi title) chromes, not just the README's 722; at 56 the grid is 232, band 312, stack **692** ≤ 700. Header pictures stay 56 (`picPx ≤ cell`), ring 56, chips 44 (G1 floor 44). The full `markKey` is kept (F3's whole point is symbol reading). The 677 combination (fi-only, 4-line title + 3-line instruction) is 15 px over and REPORTED, the same class as the base's d1.
4. **F2 keeps the design geometry (hdrH 64) with `maxEither:2`.** A first build set hdrH 68 from the base record's row budget (40 / 62.6 → 2 wraps + 4 = 305 > 304); the real pipeline measures rows at **36 one-line / 60 two-line** (m, 60 forced two-either cases under the WORST chrome), so the hypothetical worst 4 × 36 + 2 × 60 + 20 = 284 ≤ 304 and the worst column actually produced was 245 (a 6-clue case with two `either` never arose in 60 cases). F2 therefore clears 677 (stack 676) and it is asserted, not reported.
5. **F5 has NO markKey and the statements sit in a 383 px column beside a 272 × 232 grid** (`cell:56, headW:104, namePx:18`, tile inner 84 — `Francesco` 82.1 fits). At the base's 223 px text width the EN `hasNot` (225) and `holderIs` (251) statements wrap (m); at 255 they fit (`holderIs` by 4 px). At 36 px inline pictures a two-line statement row is 62.6, so the all-wrap worst case is 5 × 62.6 + 24 = 337 per band: with the key 36 + 12 + 2 × 337 + 20 = 742 > 733; without it 694 ≤ 700. The key's crossing-rule mini-grid teaches a move this face never makes (no cell is marked; the glyph pair beside each statement is the legend), so dropping it buys robustness for the wordy locales instead of a per-locale wrap cap the composer cannot see. Verify asserts band ≤ 337 (`cfg.bandMax`) and refuses a markKey on a read page (poisoned). The design's withdrawn "≤ 3 two-line statements" cap stays withdrawn.

7. **F4 propagation uses the copy rule in all three directions** (np ✓ → nc row ≡ pc row; nc ✓ → np row ≡ pc row; pc ✓ → np column ≡ nc column), not only the design's np → nc/pc rule.
